# 任务：重构 Ashen RPG 的 AI 开发 Harness 与游戏数值实验系统

仓库：https://github.com/YuxiangLiu-lyx/Ashen

你是一名资深 AI Agent Harness 工程师、软件架构师、游戏引擎工程师和 RPG 数值系统设计师。

你的任务不是撰写建议或设计文档，而是**实际检查、重构、实现和测试这个仓库，使它能够长期由 Codex 等 AI Coding Agent 稳定开发**。

完成后，新的 Codex 会话应当能够仅凭仓库内容和一个简短的用户需求，自主定位相关文件、理解现有设计、实施修改、运行验证、保存任务状态，而不需要重新阅读全部历史资料或依赖过去的聊天上下文。

同时建立可扩展的 Game Balance Lab，使未来的职业、技能、装备、任务奖励、经济成长和复杂联动能够通过真实代码驱动的模拟、统计分析与自动优化来设计和验证。

## 一、工作原则

1. 先实际检查仓库，再做架构决策。以下内容是目标，不是强制的具体实现。
2. 尽量利用现有结构、工具和测试，不为架构完整性引入不必要的复杂度。
3. Harness 应当服务于 Agent，而不是让 Agent 为维护 Harness 花费大量上下文。
4. 不依赖聊天历史作为权威信息；项目状态、规则和设计决策必须可在仓库中恢复。
5. 保持原有游戏运行、剧情、角色、存档、资源、地图和战斗行为兼容。
6. 不删除历史原件，不把恢复快照误当作完整原始开发源码。
7. 不允许为了通过测试而删除、弱化或绕过有效测试。
8. 不允许把未经验证的设计文档当成真实运行行为。
9. 现有游戏规则与新的设计意图必须区分；没有授权时，不擅自重新平衡游戏。
10. 自动选择技术方案，执行完整改造，不能停留在规划阶段。

## 二、首先检查现有项目

检查 Git 状态、远端、当前版本、仓库结构、构建过程、测试、运行入口、存档机制与历史档案。

特别注意：

- 项目为《烬誓：圣女与影刃》，当前仓库记录的版本为 V28.1，必须以实际检查结果为准。
- `dist/` 包含已恢复的实际运行模块；文件名中的旧版本号不能直接代表当前行为。
- `dist/balance-v14.js`、`dist/combat-overhaul-v28.js`、`dist/chapter5-economy-v14.js` 等文件包含与战斗、奖励和经济相关的规则，但必须继续确认其运行时引用关系。
- V28 战斗强化采用覆盖层，需识别初始化顺序、包装逻辑和真正生效的规则。
- 已有 `AGENTS.md`、`source/CURRENT_STATE.json`、`NEXT_SESSION_PROMPT.md` 和测试工具，优先兼容、整合与精简，避免产生冲突的重复权威来源。
- 当前代码是恢复后的运行快照，不得假设拥有完整原始开发历史。

在修改之前建立可重复执行的基线检查，并保存其结果。对于原本就存在的失败与限制，明确记录，不能通过修改验收标准掩盖。

## 三、构建轻量、可靠的 Agent Harness

### A. 重构项目指令系统

将根目录 `AGENTS.md` 改造成简短、稳定、可长期使用的 Agent 执行入口。

它应定义：

- 权威资料优先级与冲突解决方式
- 如何从用户需求定位相关系统
- 何时使用 Skills
- 何时创建执行计划
- 如何安全修改代码
- 如何运行验证
- 如何更新持久任务状态
- 如何执行 Git 保存和交付

避免要求 Agent 每次读取全部项目文档。

细节放在可按需检索的文件中。

需要确保 Codex 即使只收到一句简短的任务要求，也能够自动遵守开发流程。

### B. 建立项目知识地图

创建结构化的模块索引，覆盖：

- 核心运行系统
- 职业与技能
- 战斗及 Boss
- 装备、属性、掉落
- 任务与经济
- 剧情、对话和章节
- NPC、伙伴、地图
- 美术、动画、资源
- UI、存档、构建、发布

每个系统记录实际代码位置、主要入口、依赖、权威规则、相关测试和不可破坏的约束。

自动生成可以从代码推导的依赖信息；仅对无法自动推导的语义信息进行少量人工维护。

模块索引应有版本或提交关联、过期检测和更新机制。不得生成一次后长期相信可能已经过时的索引。

### C. 实现 Task-Aware Context Router

实现可运行的上下文定位工具，输入自然语言任务，返回与该任务有关的文件、模块、设计规则及测试建议。

例如：

`python3 tools/harness/context.py --task "调整暗影职业的流血连招"`

应能够发现相关技能配置、运行时实现、依赖模块、Boss 特殊规则、存档约束和测试，而不是扫描读取全部项目资料。

要求：

1. 采用结构化模块索引、关键词/符号检索、代码依赖关系等可靠且轻量的技术。
2. 优先精准检索，不默认建立复杂向量数据库。
3. 能区分当前有效代码、当前设计规范、历史资料和未来构思。
4. 输出每个候选上下文被选中的原因。
5. 支持合理的上下文预算和按需扩展。
6. 检索失败或信息冲突时显式报告，不得猜测。
7. 对文件移动、模块新增和代码修改具有更新或失效机制。
8. 为典型任务建立检索测试，既检查是否遗漏关键文件，也检查是否过量加载无关资料。

Router 负责提供发现结果，而不是假装能替代实际代码搜索或程序依赖分析。

### D. 建立 Skills 系统

按 Codex 支持的标准，在 `.agents/skills/` 建立适量专用 Skills。

至少覆盖：

- 战斗与技能修改
- 职业与装备设计
- 任务与经济修改
- 剧情与角色修改
- 美术与地图修改
- 测试、集成和发布验收

每个 Skill 都应有准确的名称、触发描述、执行步骤、必要参考资料和验证要求。

不要创建大量内容重复的 Skills，也不要让一个简单任务触发全部 Skills。

### E. 建立持久任务与设计决策系统

使用仓库中的任务文件或等效机制维护：

- 任务 ID 和目标
- 验收标准
- 基线提交
- 相关模块
- 进行中的修改
- 关键设计决策
- 已完成与未完成工作
- 测试结果及证据
- 阻塞问题
- 下一步动作

新会话必须能够直接接续尚未完成的任务。

历史任务可以归档，但不要让历史任务资料成为每次启动的默认上下文。

不允许用模型生成的文字冒充真实测试结果。

### F. 标准化执行与验证流程

实现可执行的命令，至少支持：

- 项目与 Harness 健康检查
- 上下文路由测试
- 按改动范围推荐测试
- 核心代码回归测试
- 必要的浏览器集成测试
- 构建与资源完整性检查
- 持久任务记录与代码版本一致性检查

为必要检查配置 GitHub Actions CI。

将廉价的检查与耗时的模拟分级：普通修改先运行快速检查，重大修改执行相关专项测试，完整发布执行更严格的验证。

测试失败时禁止将修改报告为成功。CI 应实际执行验证，不能仅仅检查文档中是否出现 `passed` 字样。

## 四、建立 Game Balance Lab

目标不是让 LLM 凭感觉决定数值，而是让游戏平衡可以重复实验、度量、比较和自动优化。

### A. 识别真实游戏规则

检查技能伤害、属性成长、装备加成、冷却、法力、控制、状态效果、敌人 AI、Boss 特殊机制、经验金币、任务奖励、装备获取等实现。

整理真实生效的规则与依赖关系。

优先复用或抽取现有纯函数。避免维护一套与游戏运行结果不一致的平行规则。

### B. 实现最小可信战斗模拟器

构建可以扩展的无渲染模拟环境，优先支持当前主要职业与代表性敌人。

要求：

- 固定随机种子和可重放实验
- 不同等级、装备、技能配置
- 不同玩家操作策略
- 技能使用、资源消耗、冷却与状态变化
- 普通敌人、精英怪、Boss 的差异
- 战斗事件日志与统计输出

如果现有代码强耦合浏览器或渲染环境，应逐步提取可测试的战斗核心，并通过原有运行环境进行一致性验证。

不得为了快速实现模拟器而自行虚构伤害与战斗机制。

无法准确模拟的部分必须标明限制，不能将近似结果伪装为真实游戏数据。

### C. 技能与装备联动分析

建立可查询的效果描述与联动关系，识别：

- 状态施加与消耗
- 增益叠加
- 冷却交互
- 控制效果
- 伤害放大
- 资源恢复与消耗
- 装备触发条件
- 潜在无限循环

允许搜索不同 Build 并比较其表现。

先使用可解释的搜索和启发式优化算法，不要没有必要地训练复杂强化学习模型。

### D. 建立平衡评价体系

至少考虑：

- 战斗胜率
- 击杀时间分布
- 不同玩家水平的通关情况
- 伤害、爆发和生存能力
- 技能使用价值
- Build 多样性
- 职业在不同场景中的优势和弱点
- 明显异常的技能或装备联动

评价标准必须可配置，而不是把所有职业强制优化成相同的 DPS。

### E. 建立成长和经济模拟基础

支持分析任务经验、金币收入、装备价格、制作材料、掉落、消耗品以及等级成长曲线。

模拟不同玩家路径，例如：

- 只完成主线
- 完成部分支线
- 全收集
- 频繁刷怪
- 经常战斗失败并消耗资源

识别卡关、资源不足、奖励失衡和异常刷取路径。

特别检查 V28 额外稀有装备掉落与阶段判定的边界行为。

### F. 输出机器可读实验结果

实验应保存：

- 运行代码版本
- 参数配置
- 随机种子
- 模拟数量
- 玩家策略
- 主要指标
- 统计结果
- 实验限制

提供可阅读的报告和适合后续 AI 分析的 JSON 等结构化结果。

自动优化得到的数值先作为候选配置，不能未经验证直接覆盖正式游戏规则。

## 五、分阶段实施

按照依赖关系执行：

1. 现状审计和行为基线
2. 精简 Agent 入口及建立权威规则体系
3. 模块索引、Context Router、Skills 和任务状态
4. 验证工具、CI 和 Harness 自身测试
5. Balance Lab 的真实规则接入与最小可信战斗模拟
6. 技能联动、数值分析和成长经济模拟基础
7. 完整回归、文档同步和交付

这是执行顺序，不是要求机械地创建七套独立框架。

优先确保核心 Harness 完整可用，再逐步完善数值模拟。不能为了追求表面完成度，生成缺少实际逻辑的空壳模块。

如果单轮执行资源有限，优先交付经过验证、可独立使用的部分，并留下明确的任务状态和接续入口。不要宣称未实现的功能已经完成。

## 六、验收标准

最终必须验证以下典型情况：

1. 新会话只收到“修改暗影流血连招”，可以根据仓库自动定位相关代码、规则及测试。
2. 用户要求调整第五章任务奖励时，不会默认加载全部剧情、美术和历史档案。
3. 用户要求修改地图表现时，不会无故触碰战斗经济。
4. 任务执行中上下文重置后，可以通过任务文件与 Git 状态恢复。
5. 改动模块后，上下文索引不会静默使用过期数据。
6. 关键依赖、运行时覆盖和存档兼容风险能够被识别。
7. 原有游戏可以构建、启动并通过对应的基线与回归检查。
8. Balance Lab 能运行至少一个由实际游戏规则支持、可重复的战斗实验。
9. 实验结果能够追溯到具体代码版本和参数。
10. 失败的验证不能被伪装成成功。
11. 新的 Agent 工作流在没有旧聊天历史时依然能够正常执行。

为这些场景编写自动化测试或可重复的验证流程，并提供实际结果。

## 七、Git 与资产要求

遵守项目现有备份、保存与推送规则。

保护所有未提交工作，不使用强制重置、强制推送或破坏性清理。

大型重构应使用安全的分支、提交或 worktree 隔离修改；整合前运行检查。

保存源码、文档、测试和必要配置。保留已有剧情、美术、历史原件及恢复能力。

不要提交凭据、私有环境变量或个人存档。

通过验收后，按仓库现有授权和 Git 工作流完成远端同步并核实实际提交。GitHub 同步不代表游戏站点已部署。

## 八、长期使用规范

最终在仓库中提供一个非常简短、可复制的通用新任务 Prompt 模板。

同时保证该模板不是 Harness 生效的唯一条件：即使用户直接输入自然语言开发需求，仓库中的 AGENTS、Skills、工具和测试也应该引导 Codex 执行正确流程。

以后不应要求用户重新粘贴本次大型 Prompt。

## 九、最终交付

实际完成代码与配置修改，并给出：

1. 最终架构及主要文件。
2. Harness 已实现的能力。
3. Balance Lab 已实现的能力及尚未实现的能力。
4. 真实运行的测试、结果和已知限制。
5. 一个新会话任务接续示例。
6. 一个技能或战斗修改的上下文路由示例。
7. 一个真实、可复现的数值模拟结果。
8. 提交记录、SHA 与远端同步状态。
9. 未来每次开发所需的最短使用方法。

整个过程中以可靠性、可维护性、检索精准度、较低上下文消耗和游戏内容保护为最高优先级。

现在开始检查仓库并实际实施，不要只输出设计方案。
